# ADR-010: Sequence representation in TraceProfile and stateful strategy

**Status:** Proposed  
**Date:** 2026-05-12

---

## Context

The trace adapter (M12) infers which operations tend to follow which from HAR session data. The stateful strategy (M13) consumes that sequence data to generate multi-step test flows automatically, rather than requiring teams to hand-author every flow.

A decision is needed on:
1. How operation sequences are represented in the `TraceProfile` (the persisted output of M12)
2. How the stateful strategy consumes that representation to produce executable `Flow` objects
3. What the minimum viable sequence model is — how much session structure to capture before it becomes noise

Several models were considered:

**Option A — Pairwise transition matrix:** capture the probability that operation B follows operation A within the same session. Simple to compute and store; loses multi-step context (A→B→C patterns are not captured directly).

**Option B — Full session paths:** store all observed operation sequences as literal paths (e.g. `[CreateOrder, GetOrder, PatchOrder, GetOrder]`). Complete but noisy — long sessions produce exponential path combinations; storage is proportional to session count, not operation count.

**Option C — Markov chain (first-order transition probabilities):** pairwise probabilities with a defined start distribution (which operations appear first in sessions) and a terminal marker. Compact representation that generates arbitrary-length sequences by following transition probabilities. Loses multi-step context beyond adjacent pairs but captures flow structure efficiently.

---

## Decision

Use a **first-order Markov chain** to represent operation sequences. The `TraceProfile` stores:

- A `StartProbability` map: the probability that each operation is the first call in a session
- A `Transitions` map: for each operation, the probability distribution over what operation follows next
- A special `__END__` sentinel in the transitions map representing "session ends here"
- A `MinObservedSessionLength` and `MaxObservedSessionLength` for diagnostic purposes

JSON representation within `TraceProfile`:

```json
{
  "sequences": {
    "start_probability": {
      "CreateOrder": 0.85,
      "ListOrders":  0.15
    },
    "transitions": {
      "CreateOrder": {
        "GetOrder":   0.87,
        "ListOrders": 0.08,
        "__END__":    0.05
      },
      "GetOrder": {
        "PatchOrder": 0.42,
        "GetOrder":   0.10,
        "__END__":    0.48
      },
      "PatchOrder": {
        "GetOrder":   0.65,
        "__END__":    0.35
      },
      "ListOrders": {
        "__END__":    0.80,
        "CreateOrder": 0.20
      }
    },
    "min_observed_session_length": 1,
    "max_observed_session_length": 7
  }
}
```

The stateful strategy generates `Flow` objects from this model by:
1. Sampling a start operation from `StartProbability`
2. Following transition probabilities until `__END__` is drawn or a configurable `max_steps` limit is reached (default: `max_observed_session_length`, capped at 10)
3. Producing a `Flow` where each step's `operation_id` is the sampled operation; input arguments are generated by the `ComposedGenerator` for that operation (ADR-009)

The generator runs this sampling `N` times (configurable, default 10) to produce a set of flows representing the realistic session space.

---

## Rationale

**First-order Markov chain is the right complexity/fidelity tradeoff.** Full session paths are impractical — a 100-session HAR with sessions averaging 5 operations produces a combinatorial explosion in paths. The pairwise matrix captures the essential insight: what tends to follow what. A first-order model loses second-order patterns (e.g. "after A→B, C is more likely than D"), but second-order models require substantially more data to produce reliable estimates and introduce considerably more storage and parsing complexity. For v2, the first-order model is the right starting point.

**The `__END__` sentinel is cleaner than a separate terminal probability.** It allows the transitions map to be self-contained — each row sums to 1.0 including the termination probability, which simplifies both generation (draw from the row until `__END__`) and validation (each row must sum to 1.0 ± floating point tolerance).

**`StartProbability` is essential, not optional.** Without it, the generator must arbitrarily pick a start operation — which either means uniform sampling (ignoring what traffic tells us about entry points) or hardcoding a heuristic. The start distribution is cheap to compute from HAR data and meaningfully constrains flow generation to realistic entry points.

**`max_steps` cap prevents runaway generation.** A Markov chain can theoretically loop (e.g. A→B→A→B). The `max_observed_session_length` is a natural cap; the hard cap of 10 provides a safety bound independent of the data.

**Trace-generated flows supplement, not replace, hand-authored flows.** Teams who know exactly which journeys matter should write those as hand-authored YAML flows (M13). Trace-generated flows are an automatic first pass — useful coverage with no authoring cost, but not a substitute for intentional flow design.

---

## Consequences

- The `analyze` command (M12) must parse HAR sessions — groups of entries sharing a session cookie or a configurable session key header. Session identification strategy must be documented in `bt analyze --help`.
- If HAR entries have no session boundary (all entries in one session), the analyzer treats the entire HAR as a single session. This produces a degenerate start distribution (only the first operation has `StartProbability > 0`) and a warning is logged.
- Transition rows that do not sum to 1.0 ± 0.001 are rejected by the parser with `ErrProfileMalformed`.
- Operations in the transitions map that do not appear in `profile.operations` are rejected with `ErrProfileMalformed` — the profile must be internally consistent.
- The stateful strategy must handle the case where a sampled operation has no response (e.g. the server returns 500) gracefully: log the failure, do not continue to the next step, mark the flow as failed at that step.
- `bt analyze --dry-run` prints the computed Markov chain without writing the profile, for inspection before committing.

// internal/trace/analyze/sequence_test.go

func TestSequenceExtraction(t *testing.T) {
    t.Run("start_probability sums to 1.0", func(t *testing.T) {
        profile := analyzeHAR(t, "testdata/orders_sample.har")
        total := 0.0
        for _, p := range profile.Sequences.StartProbability {
            total += p
        }
        assert.InDelta(t, 1.0, total, 0.001)
    })

    t.Run("each transition row sums to 1.0 including END sentinel", func(t *testing.T) {
        profile := analyzeHAR(t, "testdata/orders_sample.har")
        for opID, transitions := range profile.Sequences.Transitions {
            total := 0.0
            for _, p := range transitions {
                total += p
            }
            assert.InDelta(t, 1.0, total, 0.001, "transition row for %s does not sum to 1.0", opID)
        }
    })

    t.Run("CreateOrder has highest start probability in orders fixture", func(t *testing.T) {
        profile := analyzeHAR(t, "testdata/orders_sample.har")
        assert.Greater(t, profile.Sequences.StartProbability["CreateOrder"], 0.5)
    })

    t.Run("transition from CreateOrder to GetOrder is dominant", func(t *testing.T) {
        profile := analyzeHAR(t, "testdata/orders_sample.har")
        transitions := profile.Sequences.Transitions["CreateOrder"]
        assert.Greater(t, transitions["GetOrder"], 0.5)
    })

    t.Run("HAR with no session boundaries produces warning and treats as single session", func(t *testing.T) {
        var logBuf bytes.Buffer
        profile := analyzeHARWithLog(t, "testdata/no_sessions.har", &logBuf)
        assert.Contains(t, logBuf.String(), "no session boundaries")
        assert.NotEmpty(t, profile.Sequences.StartProbability)
    })

    t.Run("operations missing from profile.operations are rejected", func(t *testing.T) {
        raw := validProfileJSON()
        raw["sequences"].(map[string]any)["transitions"].(map[string]any)["UnknownOp"] = map[string]any{"__END__": 1.0}
        _, err := ParseProfile(writeTempJSON(t, raw))
        assert.ErrorIs(t, err, ErrProfileMalformed)
        assert.Contains(t, err.Error(), "UnknownOp")
    })
}

// internal/strategy/stateful/gen/flow_gen_test.go

func TestFlowGeneratorFromTraceProfile(t *testing.T) {
    profile := loadFixtureProfile(t, "testdata/orders_profile.json")

    t.Run("generates requested number of flows", func(t *testing.T) {
        flows := GenerateFlows(profile, GenerateFlowsConfig{Count: 10, MaxSteps: 5})
        assert.Len(t, flows, 10)
    })

    t.Run("each flow starts with an operation in start_probability", func(t *testing.T) {
        flows := GenerateFlows(profile, GenerateFlowsConfig{Count: 50, MaxSteps: 5})
        validStarts := keysOf(profile.Sequences.StartProbability)
        for _, flow := range flows {
            assert.Contains(t, validStarts, flow.Steps[0].OperationID)
        }
    })

    t.Run("no flow exceeds max_steps", func(t *testing.T) {
        flows := GenerateFlows(profile, GenerateFlowsConfig{Count: 100, MaxSteps: 3})
        for _, flow := range flows {
            assert.LessOrEqual(t, len(flow.Steps), 3)
        }
    })

    t.Run("all operation IDs in generated flows exist in the profile", func(t *testing.T) {
        flows := GenerateFlows(profile, GenerateFlowsConfig{Count: 50, MaxSteps: 5})
        for _, flow := range flows {
            for _, step := range flow.Steps {
                assert.Contains(t, profile.Operations, step.OperationID)
            }
        }
    })

    t.Run("flows are not all identical (generator produces variety)", func(t *testing.T) {
        flows := GenerateFlows(profile, GenerateFlowsConfig{Count: 20, MaxSteps: 5})
        unique := uniqueFlowSignatures(flows)
        assert.Greater(t, len(unique), 1, "all flows are identical — generator is not sampling correctly")
    })
}
