# M3.5 — Integration Test Suite (Replay)

This milestone exercises the replay system built in M3 against the in-repo orders API. It adds a deliberately failing case to the integration suite, verifies an artifact is produced, and confirms `bt replay` correctly identifies whether a failure is still present.

---

## Overview

M3.5 delivers two things:

1. **A failing integration test case** — a case added to the orders API test suite that is expected to fail, producing a real artifact on disk
2. **A replay smoke test in CI** — the artifact is replayed against the running orders API to confirm the replay command works end-to-end

**Exit criterion:** A deliberately failing case against the orders API produces an artifact under `.bt/artifacts/`. Running `bt replay` against that artifact correctly reports the failure. The CI pipeline captures the artifact as a build artefact.

---

## Step 1 — Add a failing case to the integration suite

### Spec

- A new case is added to `examples/orders-api/bt/tests/table.yaml` that is expected to fail
- The failure must be real — not a misconfigured expectation, but a case that exposes a genuine limitation or deliberate behaviour of the orders API
- The broken endpoint (`GET /orders/{id}/broken`) is the right target — it exists specifically for this purpose
- Because the broken endpoint returns inconsistent shapes, a status-code-only assertion will pass — the real assertion failure will come from M4.5's schema invariant. For M3.5 we use a header assertion that the broken endpoint does not set
- The case is clearly documented so it is obvious it is expected to fail
- The failing case must not block the CI pipeline — it runs in a separate `bt run` invocation that is allowed to fail, and the artifact is captured regardless

### Failing case

Add to `examples/orders-api/bt/tests/table-expected-failures.yaml`:

```yaml
# These cases are expected to fail. They exist to validate that bt produces
# artifacts correctly and that the replay system works end-to-end.
# They run in CI in a separate step that is allowed to fail (continue-on-error: true).

cases:
  # The broken endpoint deliberately omits required fields on odd-numbered calls.
  # This case asserts a header that the broken endpoint never sets, so it
  # always fails and always produces an artifact.
  - id: broken-endpoint-missing-header
    operation_id: GetOrderBroken
    input:
      method: GET
      path: /orders/ord-0001/broken
    expected:
      status_code: 200
      headers:
        X-Request-ID: "should-not-be-present"
```

Add a corresponding `backendtest-failures.yaml` config:

`examples/orders-api/bt/backendtest-failures.yaml`:

```yaml
version: 1

target:
  name: orders-api
  base_url: http://localhost:8080
  schema: ../openapi.yaml

strategies:
  - type: table
    file: ./tests/table-expected-failures.yaml

report:
  formats: [console, json]
  output_dir: ./.bt/artifacts

safety:
  profile: safe
```

### Tests

The integration test here is the CI pipeline itself — we verify the artifact is produced and the replay command runs. However, we add a local test script to make this easy to run manually:

`examples/orders-api/bt/scripts/test-replay.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

CONFIG="examples/orders-api/bt/backendtest-failures.yaml"
ARTIFACT_DIR="examples/orders-api/bt/.bt/artifacts"

echo "=== Running expected-failure cases ==="
# Allow failure — these cases are expected to fail.
./bt run --config "$CONFIG" --strategy table || true

echo ""
echo "=== Checking artifact was produced ==="
ARTIFACTS=$(ls "$ARTIFACT_DIR"/*.json 2>/dev/null || true)

if [ -z "$ARTIFACTS" ]; then
  echo "FAIL: No artifact was produced"
  exit 1
fi

echo "Artifact found:"
echo "$ARTIFACTS"

echo ""
echo "=== Replaying most recent artifact ==="
LATEST=$(ls -t "$ARTIFACT_DIR"/*.json | head -1)

# Replay against the running server — expect it to still fail.
./bt replay --config examples/orders-api/bt/backendtest.yaml "$LATEST" || true

echo ""
echo "=== Replay smoke test complete ==="
```

Make it executable:

```bash
chmod +x examples/orders-api/bt/scripts/test-replay.sh
```

## Step 2 — Update the orders API to create a seed order

The failing case references `/orders/ord-0001/broken` which requires an order to exist in the store. The CI pipeline needs to create this order before running the failure cases.

Add a setup step to the CI workflow that seeds an order via the API:

```bash
# In CI, after the API is running:
curl -s -X POST http://localhost:8080/orders \
  -H "Content-Type: application/json" \
  -d '{"amount": 100, "currency": "GBP", "description": "Seed order for M3.5"}' \
  | jq .
```

This ensures `ord-0001` exists before the broken endpoint is called.

Alternatively, update the broken endpoint handler to return a fixed response when no order exists (rather than 404), making the case self-contained. Update `handleBrokenOrder` in `examples/orders-api/handlers.go`:

```go
func handleBrokenOrder(s *store) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		brokenCallCount++
		id := r.PathValue("id")
		o, ok := s.get(id)

		if !ok {
			// For M3.5: return a consistent broken response even when
			// the order doesn't exist, so the replay case is self-contained.
			if brokenCallCount%2 == 0 {
				writeJSON(w, http.StatusOK, map[string]any{
					"id":     id,
					"status": "unknown",
				})
			} else {
				writeJSON(w, http.StatusOK, map[string]any{
					"id": id,
					// amount, currency, status intentionally omitted
				})
			}
			return
		}

		if brokenCallCount%2 == 0 {
			writeJSON(w, http.StatusOK, o)
		} else {
			writeJSON(w, http.StatusOK, map[string]any{
				"id": o.ID,
			})
		}
	}
}
```

Update the server test to reflect this:

```go
func TestBrokenEndpoint_NonExistentID_StillResponds200(t *testing.T) {
	srv := newTestServer(t)
	defer srv.Close()

	resp, err := http.Get(srv.URL + "/orders/does-not-exist/broken")
	if err != nil {
		t.Fatalf("unexpected error: %v", err)
	}
	// Broken endpoint returns 200 even for unknown IDs — by design.
	if resp.StatusCode != http.StatusOK {
		t.Errorf("expected 200 from broken endpoint for unknown ID, got %d", resp.StatusCode)
	}
}
```

## Step 3 — Update CI workflow

Update `.github/workflows/ci.yml` to add the replay smoke test:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
          cache: true

      - name: Lint
        uses: golangci/golangci-lint-action@v6
        with:
          version: latest

      - name: Unit tests
        run: go test ./... -race -coverprofile=coverage.out

      - name: Build bt
        run: go build -o bt ./cmd/bt

      - name: Build orders-api
        run: go build -o orders-api ./examples/orders-api

      - name: Start orders-api
        run: ./orders-api &
        env:
          PORT: 8080

      - name: Wait for orders-api
        run: |
          for i in $(seq 1 10); do
            curl -sf http://localhost:8080/health && break
            echo "waiting for orders-api... ($i)"
            sleep 1
          done

      # M2.5 — passing integration tests
      - name: Integration tests (passing cases)
        run: ./bt run --config examples/orders-api/bt/backendtest.yaml --strategy table

      - name: Integration tests (JSON output)
        run: ./bt run --config examples/orders-api/bt/backendtest.yaml --strategy table --output json

      # M3.5 — expected failure cases produce artifacts
      - name: Integration tests (expected failures — artifact production)
        run: ./bt run --config examples/orders-api/bt/backendtest-failures.yaml --strategy table || true

      - name: Verify artifact was produced
        run: |
          ARTIFACT_DIR="examples/orders-api/bt/.bt/artifacts"
          COUNT=$(ls "$ARTIFACT_DIR"/*.json 2>/dev/null | wc -l)
          if [ "$COUNT" -eq 0 ]; then
            echo "FAIL: No artifact was produced by the expected-failure run"
            exit 1
          fi
          echo "OK: $COUNT artifact(s) found"
          ls -la "$ARTIFACT_DIR"

      - name: Replay most recent artifact
        run: |
          ARTIFACT_DIR="examples/orders-api/bt/.bt/artifacts"
          LATEST=$(ls -t "$ARTIFACT_DIR"/*.json | head -1)
          echo "Replaying: $LATEST"
          # Replay against running server — failure is still present, so
          # bt replay exits non-zero. We allow that here.
          ./bt replay --config examples/orders-api/bt/backendtest.yaml "$LATEST" || true

      - name: Upload test artifacts
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: bt-artifacts
          path: |
            examples/orders-api/bt/.bt/
          retention-days: 7

      - name: Upload JUnit results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: examples/orders-api/bt/.bt/reports/
          retention-days: 7
```

## Step 4 — Local verification

Run the full local smoke test:

```bash
# Start the orders API
go run ./examples/orders-api &
sleep 1

# Run passing cases (should all pass)
./bt run --config examples/orders-api/bt/backendtest.yaml --strategy table

# Run expected-failure cases (should fail and produce an artifact)
./bt run --config examples/orders-api/bt/backendtest-failures.yaml --strategy table || true

# Check an artifact was produced
ls -la examples/orders-api/bt/.bt/artifacts/

# Replay the artifact
LATEST=$(ls -t examples/orders-api/bt/.bt/artifacts/*.json | head -1)
./bt replay --config examples/orders-api/bt/backendtest.yaml "$LATEST"

# Kill the background server
kill %1
```

Expected output from the failure run:

```

       response_header: header "X-Request-ID": expected "should-not-be-present", got ""

       replay:   bt replay examples/orders-api/bt/.bt/artifacts/2026-05-09T143022Z-broken-endpoint-missing-header.json

1 tests run: 0 passed, 1 failed
```

## What this proves

By the end of M3.5 the following is true for every strategy built from M4 onwards:

- Any failure automatically produces a portable artifact with no extra code in the strategy
- The artifact contains enough information to replay the failure exactly
- `bt replay` gives a developer a one-command path from "CI failed" to "I can see exactly what happened"
- CI preserves artifacts as build outputs so failures can be investigated after the fact

The broken endpoint will be revisited in M4.5 where property testing will find the schema violation automatically rather than requiring a hand-written header assertion.

## M3.5 exit criterion

A deliberately failing integration test case produces an artifact under `.bt/artifacts/`. `bt replay` correctly identifies that the failure is still present when replayed against the running orders API. CI captures the artifact as a build output with `retention-days: 7`. All passing cases from M2.5 continue to pass.
